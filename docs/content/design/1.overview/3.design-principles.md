# Design Principles

設計原則は、実装時に迷ったときの判断基準です。現在の進捗ではなく、リポジトリが維持したい理想形を記述します。

## 明示されたスコープを優先する

AI Agent は、delivery に書かれた現在スコープと対象タスクを優先します。便利そうな機能や推測した仕様は、受け入れ条件に含まれない限り追加しません。

## 責務を混ぜない

UI、API、共有契約、運用手順、開発タスクはそれぞれ置き場所を分けます。短期的に楽でも、実装状況や暫定対応を design に書きません。

## 小さく検証可能に進める

タスクは完了条件と検証方法を持ちます。実装は、レビューできる単位、テストできる単位、docs に反映できる単位で進めます。

## 共有契約を先に安定させる

複数領域にまたがるデータ構造、API の入出力、エラー形式は共有契約として扱います。アプリごとに似た型を再定義して、意味がずれる状態を避けます。

## 実装後に docs を更新する

コード変更が設計、運用、現在スコープ、受け入れ条件に影響する場合は、該当する docs を更新します。docs とコードが矛盾したまま作業を完了しません。
