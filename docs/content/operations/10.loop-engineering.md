# Loop Engineering Operations

This page defines the repeatable operations for running Loop Engineering.

## L1 Local Run

After changing Nuxt Content docs:

```bash
LOOP_BUDGET_USD=10 LOOP_ESTIMATED_COST_USD=0 LOOP_MAX_ATTEMPTS=3 pnpm loop:l1
```

Expected result:

- `STATE.md` is updated as a compatibility mirror.
- `.loop/state.json` is updated with machine-readable latest state.
- `.loop/runs/*.md` receives a per-run log.
- `docs/content/delivery/loop-dashboard.md` is updated as the human-facing latest status page.
- Changed docs are listed as candidate items.
- No implementation files outside the documented loop state surfaces are modified by the harness.

## L2 Gate

After a human approves a candidate item:

```bash
LOOP_APPROVED_ITEM_ID=<candidate-id> LOOP_ENABLE_AUTONOMY=l2 pnpm loop:l2
```

L2 may proceed only after this gate passes. Maker then implements the approved scope and Verifier runs command evidence.

Expected result:

- The L2 gate result is mirrored in `STATE.md`.
- `.loop/state.json`, `.loop/runs/*.md`, and the Loop Dashboard are updated.
- If approval or enablement is missing, the dashboard shows a blocked gate and the next human action.

## Verifier Runs

Docs verification:

```bash
pnpm loop:verify:docs
```

Web verification:

```bash
pnpm loop:verify:web
```

Harness verification:

```bash
pnpm loop:verify:harness
```

Verifier records command results in `STATE.md`, `.loop/runs/*.md`, `.loop/state.json`, and the Loop Dashboard. PR bodies may summarize the same evidence later, but repository state remains the local source for this scope.

## State Surfaces

Use these surfaces for routine operation:

| Surface | Use |
| --- | --- |
| `docs/content/delivery/loop-dashboard.md` | Human-facing current turn and next action. |
| `.loop/state.json` | Machine-readable latest state. |
| `.loop/runs/*.md` | Run-by-run evidence history. |
| `STATE.md` | Compatibility mirror for existing candidate and evidence flows. |

The Harness must not read or write secrets, credentials, tokens, `.env`, or `.env.*` values when updating these surfaces.

## Reading The Loop Dashboard

Use `docs/content/delivery/loop-dashboard.md` as the first page to inspect when checking the latest Loop Engineering state. Read it from top to bottom. The first screen answers whether the current turn is ready, blocked, verifying, or resolved, and what a human should do next.

| Section | How to read it | Human action |
| --- | --- | --- |
| Current Turn | Shows the latest run ID, mode, status, autonomy gate, owner role, and approved item. | Confirm the run and approved item match the work being reviewed. |
| Intent | Summarizes what the current turn is trying to do. | Check that the intent matches the approved task and does not expand scope. |
| Gate State | Shows the operating state such as `approved`, `blocked`, `verifying`, or `resolved`. | Continue only when the gate state allows the next operation. |
| Next Human Action | States the next decision or review expected from a human. | Treat this as the primary instruction for what to inspect or approve next. |
| Source Docs | Lists the task or docs that define the current turn. | Open these docs before approving implementation or resolution. |
| Scope Boundary | Shows the Reality Source, compatibility mirror, machine state, run logs, dashboard path, and denylist reminder. | Confirm the work stays inside the approved surface and does not touch secrets or out-of-scope systems. |
| Verification | Shows command evidence or why evidence is missing for the latest run. | Do not mark work resolved until required verifier evidence is present or a blocker is recorded. |
| Handoff Queue | Lists blockers and required human decisions. | Stop automation and resolve the listed blocker before continuing. |
| Candidate Items | Lists L1-discovered candidates and their source docs. | Use the approved item ID to find the candidate being promoted to L2 or L3. |
| Recent Runs | Links to `.loop/runs/*.md` run logs. | Read the latest run log when the dashboard summary is not enough. |

Interpret common states as follows:

| State | Meaning | Next step |
| --- | --- | --- |
| `approved` | Human approval and the autonomy gate allow the next maker action. | Maker may work inside the approved task scope and primary area. |
| `blocked` | Required approval, enablement, evidence, or a human decision is missing. | Read `Next Human Action` and `Handoff Queue`, then decide or unblock manually. |
| `verifying` | Implementation is ready for verifier commands. | Run or review the task's verification commands. |
| `resolved` | Required verifier evidence has completed the task. | No further maker work is needed unless a new task reopens scope. |

If the dashboard and task page disagree, treat the task page under `docs/content/delivery/scopes/**/tasks/*.md` as the task-level Reality Source and update generated state only after the task schema is valid.

## GitHub Actions

The L1 workflow runs on:

- pushes to `docs/content/**/*.md`,
- daily scheduled triage,
- manual workflow dispatch.

The workflow state write surface is `STATE.md`, `.loop/state.json`, `.loop/runs/*.md`, and `docs/content/delivery/loop-dashboard.md`. L2 and L3 PR automation must be added only after the promotion criteria in `design/4.loop-engineering/autonomy-tiers` are satisfied.
