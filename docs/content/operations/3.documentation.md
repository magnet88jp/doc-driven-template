# Documentation Operations

Documentation Operations は、docs の更新手順であり、AI Agent が利用者の説明を docs へ整理するための運用ルールです。

利用者は docs の置き場所を意識しなくても構いません。AI Agent は、利用者が説明した「何を作りたいか」を読み取り、理想設計、標準手順、現在スコープ、タスク、受け入れ条件へ分類してから docs を更新します。

## 基本方針

- docs 更新は、実装と同じ開発成果物として扱う。
- AI Agent は、更新前に内容を分類し、反映先を判断する。
- 利用者が `design`、`operations`、`delivery` を指定していなくても、AI Agent が適切な置き場所を選ぶ。
- 大きな判断変更は、コードより先に docs へ反映する。
- 実装後は、検証結果と docs の内容が矛盾していないか確認する。

## docs の責務分離

### design

`design` は理想形を書く場所です。最終的に目指す構成、責務境界、アーキテクチャ、設計原則、長期的な判断基準を記述します。

`design` には、現在の進捗、暫定対応、未完了タスク、個別ブランチの事情を書きません。現在まだ実装されていない理想形であっても、長期的に目指す判断基準であれば `design` に置きます。

### operations

`operations` は繰り返し使う標準手順を書く場所です。初期設定、日次、週次、月次、アドホック対応、環境情報、ドキュメント更新手順などを記述します。

`operations` には、特定タスクだけの暫定作業、今回だけの回避策、開発途中の進捗を書きません。担当者が変わっても同じ結果になる手順だけを置きます。

### delivery

`delivery` は現在の開発を管理する場所です。ロードマップ、現在スコープ、理想設計との差分、タスク、受け入れ条件、検証方法を記述します。

`delivery` には、今作る範囲、今回は作らない範囲、理想形との差分、実装対象タスク、完了条件を書きます。AI Agent が実装前に読む入口は `delivery` です。

## 置き場所の判断

| 内容 | 反映先 |
| --- | --- |
| 理想形、責務境界、アーキテクチャ、設計原則 | `design` |
| 標準手順、環境情報、繰り返す運用確認 | `operations` |
| 現在スコープ、差分、タスク、受け入れ条件、検証方法 | `delivery` |
| 実装だけが変わり、合意内容が変わらない | docs 更新なしでもよい |

理想形と現在スコープは分けて扱います。理想形は「最終的にどうあるべきか」、現在スコープは「今回どこまで作るか」です。理想形が大きくても、現在スコープは小さく切って構いません。

## AI Agent 向け分類ルール

AI Agent は、利用者の説明を受けたら、まず次の分類に分けます。

1. 理想設計: 長期的に目指す構成、責務、判断基準。
2. 標準手順: 繰り返し使う作業、確認、運用ルール。
3. 現在スコープ: 今回作る範囲、今回は作らない範囲、前提。
4. タスク: 実装可能な単位に分けた作業。
5. 受け入れ条件: 何が確認できれば完了と言えるか。

分類できない情報がある場合は、無理に docs へ書き込まず、追加質問または仮置きの前提として扱います。利用者に docs の置き場所を尋ねるのではなく、何を実現したいのか、今決めたいのか、後回しにしたいのかを確認します。

## AI Agent への標準依頼パターン

### 新規プロジェクト開始

```txt
このリポジトリで作りたいものを説明します。
まずコードは変更せず、必要であれば追加質問してください。
その後、design、operations、delivery を整理してください。
docs の置き場所は AI Agent が判断してください。
```

### 設計思想作成

```txt
作りたいものを元に、理想設計と判断基準を整理してください。
現在スコープ、タスク、進捗は design に混ぜず、必要に応じて delivery に分けてください。
```

### スコープ追加

```txt
次に作りたい範囲を追加したいです。
理想設計との差分、In Scope、Out of Scope、受け入れ条件を整理してください。
必要な design / operations の更新があればあわせて提案してください。
```

### タスク作成

```txt
現在スコープを、AI Agent が実装できるタスク単位に分解してください。
各タスクには Goal、Scope、Out of Scope、Acceptance Criteria、Verification を含めてください。
```

### 実装

```txt
次のタスクを実装してください。
実装前に Current Scope、対象タスク、関連する design / operations を読んでください。
実装後は検証し、docs と実装がずれていれば必要な docs を更新してください。
```

### docs 更新

```txt
次の変更内容を docs に反映してください。
design、operations、delivery のどこへ書くべきかは AI Agent が判断してください。
無関係な文体変更や設計刷新は混ぜないでください。
```

## AI Agent の判断ルール

AI Agent は、利用者の依頼を受けたら、すぐにファイルを書き換える前に次を判断します。

1. 依頼は理想設計、標準手順、現在スコープ、タスク、受け入れ条件のどれに関係するか。
2. 既存 docs のどのページと矛盾または重複するか。
3. 今回の更新は、コードより先に合意すべき内容か。
4. 実装後に docs を更新すれば足りる内容か。
5. 利用者に追加質問しないと分類できない内容か。

利用者が「design に書いてください」のように指定していなくても、AI Agent はこのルールに従って反映先を判断します。利用者が置き場所を指定した場合でも、責務分離に反するなら、より適切な反映先を提案してから更新します。

## 更新手順

1. 変更が `design`、`operations`、`delivery` のどこに影響するか確認する。
2. 既存 docs を読み、重複、矛盾、古い記述を確認する。
3. 該当する Markdown を更新する。
4. `title`、`description`、`navigation icon` を含む frontmatter を保つ。
5. docs サイトが Nuxt Content として読める構造を保つ。
6. 実装後の検証結果と docs の内容が矛盾していないか確認する。

## 更新範囲の制限

実装後に docs を更新する場合、現在のタスク完了に必要な範囲へ絞ります。無関係な設計刷新、文体変更、ページ構成変更を混ぜません。

新規プロジェクト開始やスコープ整理のように docs 構造そのものを作る依頼では、必要な範囲で `design`、`operations`、`delivery` を横断して整理します。
