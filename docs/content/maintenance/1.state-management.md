# Loop State Management

Loop Engineering state is split across four repository artifacts. Nuxt Content under `docs/content/` remains the Reality Source for agreed scope and task state.

| Artifact | Responsibility |
| --- | --- |
| `docs/content/delivery/loop-dashboard.md` | Human-facing latest status surface. It shows the current turn, intent, gate state, next human action, source docs, verification, handoff queue, and recent runs. |
| `STATE.md` | Compatibility mirror and operational shortcut for existing Harness flows. It preserves candidate tables and historical evidence, but it is not the primary human dashboard. |
| `.loop/state.json` | Machine-readable latest loop state generated by the Harness. Agents and future tools may read this when they need structured current-turn data. |
| `.loop/runs/*.md` | Append-only run logs for individual Harness, gate, and verifier runs. These logs preserve evidence without deleting older `STATE.md` history. |

## Migration Rule

Existing verifier evidence in `STATE.md` must not be deleted during state separation. The Harness may append to `STATE.md` for compatibility, then write `.loop/state.json`, `.loop/runs/*.md`, and the Nuxt Content dashboard from the same run summary.

If a migration would destroy existing verifier evidence, stop and record a handoff condition.

## State Sections

`STATE.md` keeps these sections as a compatibility mirror:

| Section | Purpose |
| --- | --- |
| Runtime Policy | Current caps, tier, and write surface. |
| Readiness Score | Promotion readiness for L2 and L3. |
| Candidate Items | L1 output and L2 input. |
| Active Work | Current maker or verifier work. |
| Verification Evidence | Command evidence and result records. |
| Resolved Items | Completed items with evidence. |
| Handoff Queue | Items blocked by policy, ambiguity, budget, or repeated failure. |
| Loop Run Log | Legacy chronological run history mirrored for compatibility. |

`.loop/state.json` keeps the latest machine state with:

- `schemaVersion`,
- `generatedAt`,
- `sourceOfTruth`,
- `humanDashboard`,
- `compatibilityMirror`,
- `currentTurn`,
- `policy`,
- `sourceDocs`,
- `verification`,
- `handoff`,
- `candidates`,
- `recentRuns`.

`.loop/runs/*.md` keeps one run per file with timestamp, mode, result, approved item, summary, source docs, verification evidence, and handoff notes.

## Candidate State Transitions

```mermaid
stateDiagram-v2
  [*] --> L1_ANALYZED
  L1_ANALYZED --> APPROVED: human approval
  L1_ANALYZED --> REJECTED: not needed
  APPROVED --> IN_PROGRESS: maker starts
  IN_PROGRESS --> VERIFYING: maker completes
  VERIFYING --> RESOLVED: verifier evidence passes
  VERIFYING --> NEEDS_FIX: verifier fails
  NEEDS_FIX --> IN_PROGRESS: attempts < 3
  NEEDS_FIX --> HANDOFF: attempts >= 3
  APPROVED --> HANDOFF: denylist or scope conflict
```

## Required Candidate Fields

Each candidate must include:

- ID,
- stage,
- approval status,
- attempts,
- source docs,
- impact area,
- maker action,
- verifier expectation.

## Task Schema State

Loop task Markdown under `docs/content/delivery/scopes/**/tasks/*.md` is the Reality Source for task-level state. The Harness validates these fields before a Maker or Verifier treats a task as actionable.

Required task fields:

- `id`
- `status`
- `autonomy`
- `source_of_truth`
- `primary_area`
- `acceptance_criteria`
- `verification_commands`
- `handoff_conditions`
- `last_evidence`

Allowed `status` values:

- `planned`: defined but not approved for implementation.
- `approved`: approved target task.
- `in_progress`: maker work is underway.
- `verifying`: verifier commands are the next action.
- `resolved`: verifier evidence completed the task.
- `blocked`: handoff condition or blocker prevents progress.

Allowed `autonomy` values:

- `manual`: inspect and report only.
- `assisted`: edit only within approved task scope and `primary_area`.
- `autonomous`: act within task schema, harness gates, denylist, budget, and verifier requirements.

`verification_commands` and `handoff_conditions` must be non-empty. A task without either field cannot move into maker or verifier work because the loop cannot prove completion or know when to stop.

## Handoff Rules

Move to handoff when:

- attempts reach three,
- budget is exceeded,
- denylisted paths are required,
- docs conflict cannot be resolved,
- verification fails twice for the same cause,
- credentials or external permissions are required.

## Secret Policy

State artifacts must not contain secret values. Harness state generation must not read or write credentials, tokens, `.env`, or `.env.*` values. Secret-like values required for runtime verification are handled outside this repository state and must be recorded only as a blocker or human handoff.
