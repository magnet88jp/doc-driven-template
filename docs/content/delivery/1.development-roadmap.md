# Development Roadmap

ロードマップは、理想設計に向けてどの順序で整備するかを示します。詳細な実装タスクは各 scope に置きます。

## Loop Engineering Implementation Roadmap

Loop Engineering は、AI Agent に同じ指示を繰り返す仕組みではありません。Nuxt Content を Reality Source とし、人間と Agent が同じ docs を見ながら、何を作りたいのか、今から何を作るのか、何をもって完了とするのかを確認できる閉ループとして実装します。

この roadmap の実装 phase は `docs/content/delivery/scopes/2.loop-engineering-turn-foundation/1.overview.md` で管理します。

このテンプレートでは、Loop Engineering の 1 turn を次の流れとして扱います。

```txt
discover -> brief -> approve -> make -> verify -> persist -> schedule
```

この流れは、Discovery、Handoff、Verification、Persistence、Scheduling を持つ制御ループです。L1、L2、L3 などの呼び名は内部の成熟度や権限境界として使いますが、利用者体験としては「docs を更新すると Agent が次の turn を組み立て、人間が docs 上で意図と検証条件を確認できる」状態を目指します。

### Implementation Order

1. Reality Source の task schema を固める。
   - 各 task Markdown に `id`、`status`、`autonomy`、`primary_area`、`acceptance_criteria`、`verification_commands`、`handoff_conditions`、`last_evidence` を持たせる。
   - `status` は `planned`、`approved`、`in_progress`、`verifying`、`resolved`、`blocked` を基本とする。
   - Agent は `STATE.md` だけでなく、Nuxt Content の task status から次の候補を発見する。

2. Loop state を分離する。
   - `STATE.md` は最新状況を人間が読むための薄い dashboard にする。
   - 機械可読な状態は `.loop/state.json` に置く。
   - 実行ログと verifier evidence は `.loop/runs/*.md` に蓄積する。
   - Persistence は残しつつ、現在状態、履歴、証跡を混ぜない。

3. PR brief 生成を実装する。
   - `pnpm loop:brief <task-id>` または同等の command を追加する。
   - brief には対象 docs、関連 docs、scope、out of scope、変更予定領域、Maker checklist、Verifier checklist、handoff triggers を含める。
   - 人間は実装前に Nuxt Content と brief を見て、Agent が何を作ろうとしているか確認できる。

4. Maker と Verifier を分離する。
   - Maker は approved task の実装だけを担当する。
   - Verifier は diff、acceptance criteria、verification commands、docs-code drift を確認する。
   - 作った Agent が自分の成果を完了判定しないように、role と prompt を分ける。

5. Nuxt Content に Active Loop Dashboard を追加する。
   - Current Vision、Current Scope、Active Tasks、Next Candidate、Last Verifier Evidence、Blocked/Handoff、Recently Resolved を表示する。
   - 人間が docs site を見れば、Agent が何を作っていて、どこで止まっているのかを把握できる状態にする。

6. GitHub Actions を turn 単位に分ける。
   - docs 変更時は discovery を実行する。
   - manual dispatch で brief を生成する。
   - approved task に対して maker/verifier を実行する。
   - PR 作成や PR body 更新は verifier evidence が残る段階までに限定し、自動 merge は対象外にする。

7. 低リスク task だけ自動 PR 化する。
   - documentation-only synchronization、低リスクな script 更新、verification metadata 更新に限定する。
   - authentication、secrets、deployment credentials、広範な architecture 変更、scope expansion は必ず handoff する。

## Stage 1: MVP

Document Driven Monorepo の docs baseline を作ります。design、operations、delivery の責務分離を定義し、AI Agent が実装前に読む Current Scope、Task、Implementation Flow を整備します。

Loop Engineering の基盤も Stage 1 に含めます。Nuxt Content を Reality Source とし、L1 影響分析、L2 承認済み実装、Verifier 証跡、将来の PR 作成までを一連のパイプラインとして設計します。

## Stage 2: Web App Baseline

`apps/web` を現在のテンプレート状態から、docs で合意した Web アプリの baseline に近づけます。画面構成、API、状態、検証方法を delivery で定義してから実装します。

この段階では、Loop Engineering の L2 を使い、人間が承認した candidate item だけを Maker が実装し、Verifier が証拠付きで検証します。

## Stage 3: Shared Contracts Baseline

API 入出力や共通型を整理し、必要に応じて `packages/shared` を追加します。共有契約の配置、依存方向、検証方法を明確にします。

L2 が安定している場合、低リスクな docs-code 同期タスクに限定して L3 の dry run を検討します。

## Stage 4: Batch and Infra Expansion

必要になった時点で `apps/batch` と `infra` を追加します。追加前に design の責務境界と operations の運用手順を更新します。
