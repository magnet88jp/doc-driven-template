# Implementation Flow

Implementation Flow は、AI Agent が実装前後に従う標準手順です。実装は docs で合意された範囲に限定します。

## Required Reading

AI Agent は実装前に必ず以下を読みます。

1. Current Scope: `docs/content/delivery/2.current-scope.md`
2. Target Task: `docs/content/delivery/scopes/**/tasks/*.md`
3. Implementation Flow: `docs/content/delivery/3.implementation-flow.md`
4. Target Task に記載された Related Docs
5. Loop Engineering task の場合は `docs/content/design/4.loop-engineering/` と `docs/content/maintenance/`

## AI Agent Prompt Template

```txt
次のタスクを実装してください。

Task:
[ここに対象 task file path を貼る]

実装前に以下を読んでください。

- docs/content/delivery/2.current-scope.md
- docs/content/delivery/3.implementation-flow.md
- Task に書かれた Related Docs
- 関連する design / operations

実装は Task の Scope に限定してください。
Out of Scope に含まれる作業は実装しないでください。

実装後は Verification を実行し、結果を報告してください。
docs と実装がずれた場合のみ、関連 docs を最小限更新してください。
```

## Loop Engineering Prompt Template

```txt
STATE.md の candidate item を L2 相当で実装してください。

Candidate:
[STATE.md の candidate ID と該当ログ]

実装前に以下を読んでください。

- docs/content/delivery/2.current-scope.md
- docs/content/delivery/3.implementation-flow.md
- docs/content/design/4.loop-engineering/*
- docs/content/operations/10.loop-engineering.md
- docs/content/maintenance/*
- Candidate に関連する Reality Source docs

Maker は approved candidate の Scope に限定して実装してください。
Verifier は typecheck、lint、test、build、または task に記載された Verification を実行し、証拠がない場合は完了扱いにしないでください。
```

## Task Requirements

Task には、AI Agent が実装前に判断できるように次の項目を含めます。

- `id`
- `status`
- `autonomy`
- `source_of_truth`
- `primary_area`
- `acceptance_criteria`
- `verification_commands`
- `handoff_conditions`
- `last_evidence`
- Goal
- Scope
- Out of Scope
- Related Docs

Schema field は frontmatter を優先します。既存 Markdown との互換のため、`Primary Area`、`Acceptance Criteria`、`Verification` などの見出しから読み取れる情報も使えますが、Loop Engineering scope の新規 task は frontmatter に machine-readable field を置きます。

## Task Schema

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Stable task ID. Example: `LE-01`. |
| `status` | yes | Current task state. Allowed values are `planned`, `approved`, `in_progress`, `verifying`, `resolved`, `blocked`. |
| `autonomy` | yes | Allowed automation level. Allowed values are `manual`, `assisted`, `autonomous`. |
| `source_of_truth` | yes | Nuxt Content task path or paths that define the task. Values must point at repository docs, usually under `docs/content/`. |
| `primary_area` | yes | Files, directories, or docs the maker may change for this task. |
| `acceptance_criteria` | yes | Concrete completion criteria. |
| `verification_commands` | yes | Commands Verifier must run, or explicitly record as blocked. |
| `handoff_conditions` | yes | Conditions that stop automation and require human decision. |
| `last_evidence` | yes | Latest verifier evidence summary, evidence path, or `pending`. |

## Status Discipline

| Status | Meaning | Implementation Gate |
| --- | --- | --- |
| `planned` | Task exists but is not approved for implementation. | Stop before implementation. |
| `approved` | Human-approved target task. | Maker may start if autonomy also allows the action. |
| `in_progress` | Maker is implementing the approved task. | Maker may continue within `primary_area`. |
| `verifying` | Implementation is ready for verifier commands. | Maker stops; Verifier runs evidence commands. |
| `resolved` | Verifier evidence passed and the task is complete. | Stop unless a new task reopens work. |
| `blocked` | Handoff condition or unresolved blocker exists. | Stop and record blocker. |

## Autonomy Discipline

| Autonomy | Meaning |
| --- | --- |
| `manual` | Agent may inspect and report only. Human performs writes and external actions. |
| `assisted` | Agent may edit within `primary_area` after the task is `approved` or `in_progress`; human approval is required for broader action. |
| `autonomous` | Agent may execute the documented loop action within task schema, harness gates, denylist, budget, and verification requirements. |

## Schema Field Writing Rules

- Put machine-readable schema fields in task frontmatter when creating or updating Loop Engineering tasks.
- Write list fields as YAML arrays, even when the field has one item.
- `source_of_truth` must point to the task Markdown or Nuxt Content docs that define the task.
- `primary_area` must list the files or directories the Maker may change.
- `acceptance_criteria` must be concrete enough for a Verifier to mark pass or fail.
- `verification_commands` must contain exact commands, one command per item, with no secret, credential, token, or `.env` value.
- `handoff_conditions` must describe concrete stop conditions that require human decision.
- `last_evidence` starts as `pending` and is replaced by a verifier evidence summary, evidence path, or blocker note.

## Pre-Implementation Schema Gate

Before editing files, Agent, Harness, and Verifier must pass the target task through the schema gate.

Stop before implementation when:

- any required schema field is missing or empty,
- `status` is not one of `planned`, `approved`, `in_progress`, `verifying`, `resolved`, `blocked`,
- requested maker work targets a task whose `status` is not `approved` or `in_progress`,
- requested verifier work targets a task whose `status` is not `verifying` or `in_progress`,
- `autonomy` is not one of `manual`, `assisted`, `autonomous`,
- `autonomy` does not allow the requested action,
- `source_of_truth` is missing, empty, or points outside repository docs without explicit task justification,
- `verification_commands` is missing or empty,
- `handoff_conditions` is missing or empty.

## Implementation Steps

1. Current Scope を読み、今回の作業が In Scope か確認する。
2. 対象 Task を読み、schema required fields、Goal、Scope、Out of Scope、Acceptance Criteria、Verification を確認する。
3. Pre-Implementation Schema Gate を通し、実装可能な `status` と `autonomy` であることを確認する。
4. 対象 Task の Related Docs と design の関連ページを読み、責務境界と理想設計を確認する。
5. 対象コードと既存 docs を確認する。
6. 実装する。
7. Verification に書かれた確認を実行する。
8. 変更内容に応じて docs を更新する。
9. 実装結果、検証結果、未実施の検証を報告する。

## Loop Engineering Steps

1. Nuxt Content を更新する。
2. `pnpm loop:l1` を実行し、`STATE.md` に candidate item を生成する。
3. 人間が candidate item を承認する。
4. `LOOP_APPROVED_ITEM_ID=<id> LOOP_ENABLE_AUTONOMY=l2 pnpm loop:l2` で L2 gate を通す。
5. Maker が承認済み範囲だけ実装する。
6. Verifier が Verification を実行し、証拠を記録する。
7. 実装結果が Reality Source とずれた場合は、該当 Nuxt Content docs を更新する。
8. PR 作成に必要な要約、検証証跡、リスクを整理する。

## Docs Update Matrix

| 変更内容 | 更新先 |
| --- | --- |
| 理想設計、責務境界、アーキテクチャが変わる | `design` |
| 標準手順、環境情報、運用確認が変わる | `operations` |
| 現在スコープ、タスク、受け入れ条件が変わる | `delivery` |
| 状態遷移、検証証跡、PR ライフサイクルが変わる | `maintenance` |
| 実装だけが変わり合意内容は変わらない | docs 更新なしでもよい |

## Guardrails

- Task の Out of Scope に含まれる作業を実装しない。
- 仕様が docs にない場合は、既存設計から導ける最小限に留める。
- 大きな判断変更は、コードより先に docs を更新する。
- 実装後に docs とコードが矛盾していないか確認する。
- Verifier の command evidence がない場合、完了扱いにしない。
